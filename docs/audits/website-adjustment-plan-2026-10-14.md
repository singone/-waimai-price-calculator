# 网站目的与后台差异筛选计划

修订日期：2026-10-14。本文替代此前“尽量对齐后台”的计划；已按任务单完成默认值、参考券与最低价择券修正，真实门店配置核对和应用仍待证据，详见任务单实施进度。

## 先明确网站目的

网站是门店定价、活动设计和组合风险测算工具。结合用户本次明确的口径，后台核对服务于以下决策：

1. 商品及套餐在最大可用优惠下，顾客最低能付多少钱。
2. 在这套优惠下，商家实际承担多少、到手多少，扣除成本后是否亏损或低于经营底线。
3. 哪些售价、券门槛、加码或凑单组合需要调整，才能兼顾支付吸引力和经营安全。

本次最低价核算不预测平均成交价、用户资格分布或活动使用概率。网站可以把后台复杂条件简化为人工核定的金额和范围；只要简化不改变上述决策，就无需复制后台功能、字段或操作流程。

网站其他模块仍有各自职责：活动设计围绕目标支付区间和最低到手边界生成路线；定价评估按商品类型和成本占比建议价格；测算结果负责暴露利润风险。不能把“最低价”机械地替换成所有模块的唯一优化目标，也不因后台差异改变这些职责。

目的依据：[项目说明](../../README.md)、[活动设计需求](../activity-design-requirements.md)、[定价评估需求](../pricing-evaluation-requirements.md)、[定价策略模型](../pricing-strategy-model.md)，并以用户本次明确的最低价口径为准。部分旧文档保留平均值或早期公式，不能据此把本次任务扩大为平均成交预测或全站重构。

## 什么差异值得处理

逐项判断：差异是否改变最低实付、对应商家承担/到手、商品成本、可售组合或经营建议？改变才进入修正范围；现有字段能表达则只修配置；现有功能无法表达且确实影响结果才开发。名称、展示、后台结构等差异默认接受。

最低价和商家利润必须来自同一个可行优惠组合。核对最大可叠加码时不相加互斥优惠；这是金额录入的核对规则，无需为此开发逐单资格引擎。若另外检查最低利润，要独立标注，不能声称它总与最低实付是同一个组合。

## 精简后的执行顺序

1. 确认当前网站真实门店配置，对照后台核对影响金额的输入：售价、成本、上下架、折扣范围、门槛、最大加码、商家/平台承担和费用。
2. 优先修5条规格绑定、缺券、门槛和最大加码；能用现有维护与同步入口解决的，全部按配置任务处理。
3. 用代表组合核算最低价和对应到手，定位现有功能的实际缺口，再决定小额加码、折扣范围或选券逻辑是否需要修改。
4. 验收修正后的经营结论，不以字段、活动数量或页面是否与后台一致作为完成标准。

## 验收口径

- 每平台选标准份单点、饭团＋饮品、双人餐，并补优惠门槛前后与凑单跨档组合。
- 对每个组合列出原价/包装、可用折扣、最大可行优惠、最低实付、商家/平台承担、费用、到手和成本；各项来自同一优惠组合。
- 已读取追加范围内，109减27最大加码4，40减12为3，60减18、90减22、128减32为2，15减10为1；其他追加未核实前，不称为完整最大值。
- 使用0.01与40元等门槛检查边界；校验加一个低价小吃是否触发更大优惠、导致到手或利润下降。
- 真实普通订单只用于验证费用和分摊，不能要求其等于最大优惠下的最低价。不要求核对平均成交价。
- 对未影响测算的后台差异明确“接受差异”；不把D05、D06、D07重新包装成其他开发任务。

本轮不建设后台镜像、活动身份管理系统、人群时段模拟、库存同步、全量平台规则引擎或自动发布。开发遵循KISS/YAGNI：配置先行，只补已证实影响决策的缺口；复用现有金额计算和同步链路，避免重复实现。
